# Agentic RAG：法规检索的充分性自评与按需补检（P3，2026-08-29）

## 解决什么问题

`regulation_match` 的基础召回（语义 + 关键词 + 图谱三路 RRF）是"文本相似"驱动的
一次性检索：营销文案换个说法、或文档横跨多个监管主题时，召回的条款可能漏掉
关键主题，而下游 LLM 审查只能基于这批条款作判断——**检索的盲区直接变成审查的盲区**。

P3 在检索层引入一个**有界 agent 循环**（`src/services/agentic_retrieval.py`）：

```
基础召回（三路 RRF）
  → LLM 自评：当前条款是否覆盖文档涉及的主要监管主题？
      ├─ 充分 → 结束（仅 1 次 LLM 评估）
      └─ 不充分 → 生成 1-3 个监管术语化补检查询（如"销售适当性管理"）
              → 逐查询混合检索 → 与既有召回 RRF 融合 → 复评/收敛
```

## 成本护栏

| 护栏 | 默认值 | 说明 |
|---|---|---|
| 功能开关 `workflow.agentic_retrieval` | **false** | LLM 成本/延迟属可选增强，缺省关（与 rerank 同先例）；未配置 `DASHSCOPE_API_KEY` 时即使开启也静默跳过 |
| 轮次上限 `workflow.agentic_max_rounds` | 2 | 基础召回后至多 1 轮补检 → **常规开销 = 每任务 1 次 LLM 评估** |
| 每轮补检查询数 | ≤ 2 | 评估提示词强制 1-3 个，服务层截到 2 |
| 提前收敛 | — | 补检结果与既有召回全为重复条款 → 立即停止（不再复评） |
| 评估自纠错 | 1 次重试 | 输出无法解析时带错误示例重试一次，仍失败则放弃补检 |

## 降级链路

| 故障 | 行为 |
|---|---|
| 未配置 API key | `get_llm()` 返回 None → 跳过，保持基础召回 |
| LLM 调用失败 / 输出两次均不可解析 | 放弃补检，基础召回原样返回 |
| 补检查询检索失败 | 单查询失败跳过，其余继续 |
| `agentic_refine` 意外异常 | 节点层捕获，保留基础召回 |

任何故障都**不改变存量行为**：agentic 只在基础召回之上做增量。

## 可观测性

节点输出新增 `retrieval_meta`（进入 ReviewState）：
`rounds`（检索轮数）/ `queries`（实际执行的补检查询）/ `added`（补检新增条款数）/
`sufficient`（最终判定，None=评估失败）/ `verdict_reason` / `usage`（评估 LLM token 累计）。
日志在补检发生时输出新增条款数与查询词，便于审计检索行为。

## 启用方式

```yaml
# configs/app.yaml
workflow:
  agentic_retrieval: true    # P3 Agentic RAG（缺省关）
  agentic_max_rounds: 2      # 可选：总检索轮数上限
```

## 测试与边界（诚实清单）

- 单测 12 例（`tests/unit/test_agentic_retrieval.py`）：判定解析、充分即停、
  补检融合、无新增收敛、轮次上限、LLM 失败降级、节点开关/缺 key/异常路径，全离线。
- 尚未做：评估器本身的准确率校准（"评估员说充分"是否真的充分）需要一批真实文档
  的人工对照——依赖影响中心真实使用后回流；补检查询目前只走混合检索（不重复触发
  图谱多跳），因为多跳已由 P2 在融合阶段独立补位。
- `true` tool-calling 形态（LLM 主动调检索工具）已在 llm_scan 落地（Function Calling
  查证）；本模块刻意用"结构化判定 + 受控循环"而非自由工具循环，为的是检索层成本
  可预算、行为可审计。
